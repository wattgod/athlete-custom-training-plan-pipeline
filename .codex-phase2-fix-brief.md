## Blocker 2 — the page must report authority, not status labels

- The page's approved/valid rendering must derive from
  `approval_matches_release` (complete, current, seal-bound snapshot), not
  from `status in {APPROVED, APPLIED, CONFIRMED}`.
- An incomplete/stale/legacy approval renders a loud non-success
  remediation state ("approval not authoritative — regenerate/re-approve")
  and exposes no later action.
- A valid approval renders the persisted snapshot dispositions (what was
  actually approved), not the live catalog.
- Regressions: page-route tests for missing snapshot entries, changed
  values/types, seal-field mismatch, old snapshot versions — each must
  show the remediation state, never "Approved".

## Blocker 3 — revocation cascades; bearer hygiene

- Bundle/download tokens minted from a review session must be revoked when
  the parent review `jti` is revoked: record the parent jti in derived
  token claims (or a parent→children index in the revocation store) and
  check the chain at verification.
- Review-bundle responses: `Cache-Control: no-store`.
- Stop putting bearer tokens in URL query strings where feasible for the
  page's own links — prefer a short-lived POST exchange or same-session

- Regressions: revoke parent → previously-minted bundle URL returns 401/403;
  bundle response header is no-store; derived-token TTL bounds.
